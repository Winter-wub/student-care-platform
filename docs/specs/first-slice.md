Spec for the first slice of the harpseal Core, synthesised from the wayfinder map [Map: spec of the first slice](https://github.com/Winter-wub/student-care-platform/issues/1) (11 resolved tickets, 3 prototype branches). Vocabulary is `GLOSSARY.md`; decisions in `docs/adr/0001`, `0003`, `0005`, `0006`, `0007` apply. Thai terms follow the English ones on first use.

## Problem Statement

A faculty office wants to reach its students over the chat apps the students already use (LINE and Telegram), know that each chat account really belongs to a given Student (นักศึกษา), send announcements to the right group and see who has read them, within the free/paid message limits of those platforms, under PDPA (consent, audit, data stays with the customer). Today this is done by hand in group chats: no identity, no targeting, no acknowledgement, no record.

The team building it wants a **reusable Core** so that the next customer is a configuration and a few Modules, not a rewrite, and so that one codebase runs both on Cloudflare Workers (cheap, no servers) and self-hosted on a single binary.

## Solution

`harpseal`: an open-source Rust Core (Apache-2.0) that a Deployment (การติดตั้งของลูกค้า) assembles from Channels, Modules and a runtime. The first slice proves the channel layer end to end:

roster import → Consent → email OTP Verification → Link → Menu → announcements to an Audience with acknowledgement → usage/quota page → one Mini App page → the minimum back office with Staff login and audit log → Job runner → `deployments/example` (a fictional university) → CI, on LINE, Telegram and a Fake Channel through one contract test suite.

## User Stories

Students (นักศึกษา)
1. As a Student, I want to add the faculty's LINE account or open its Telegram bot and be greeted in Thai, so that I know I am in the right place.
2. As a Student, I want to read a short privacy notice with a link to the full text before giving any data, so that I can decide whether to continue.
3. As a Student, I want to type my student ID and receive a one-time code at my university email, so that nobody else can claim my identity.
4. As a Student, I want clear messages when my ID is malformed, not on the roster, has no email on file, or is already linked elsewhere, so that I know what to do next.
5. As a Student, I want to resend the code or cancel while waiting for it, so that a lost email does not block me.
6. As a Student, I want to be told how many attempts remain and when a lockout ends, so that I am not confused by silence.
7. As a Student, I want the chat Menu to unlock the moment Verification succeeds and to see the Menu entries once in the chat, so that I can start using it without searching.
8. As a Student, I want to receive announcements for my programme/year/group in my own language (Thai by default), so that I only get what concerns me.
9. As a Student, I want a "รับทราบ" button on announcements that require it, and a confirmation when I press it again, so that I can prove I read it.
10. As a Student, I want a Menu entry showing my 5 latest announcements with unacknowledged ones first, and a way to see all of them, so that I can catch up.
11. As a Student, I want a Mini App page (LIFF / Telegram Web App) showing my Link status and my announcements with acknowledge buttons, so that I can read long content comfortably.
12. As a Student, I want to unlink my account from the chat Menu after a confirmation, so that I control my data.
13. As a Student who blocked and later unblocked the bot, I want to be welcomed back without redoing Verification, so that I do not lose access.
14. As a Student, I want to be shown a new privacy notice version before continuing when it changes, so that my consent is current.
15. As a Student who types free text or sends a file, I want one polite reply pointing at the Menu (not one per message), so that I am not spammed.
16. As a Student with a linked account on another channel, I want a warning when someone tries to link my ID from a new account, so that I can report misuse.

Staff (เจ้าหน้าที่)
17. As a Staff member, I want to log in with email and password and stay logged in for a work day, so that I can do my job without friction.
18. As a Staff member, I want to upload the roster as CSV or XLSX, see a preview of what will change (new/updated/left/skipped) and the rows that are invalid, so that I never corrupt the roster.
19. As a Staff member, I want to choose "whole roster" or "add/update only" at upload, so that a partial file does not mark everyone as left.
20. As a Staff member, I want a progress page for a running import and to be prevented from starting a second one, so that large files are safe.
21. As a Staff member, I want to see the roster, search by name or code, open a Student and see their Links per Channel, Tags, Consent and attributes, so that I can help students.
22. As a Staff member, I want to edit a Student's fields by hand and have my edits survive the next import until I say otherwise, so that corrections stick.
23. As a Staff member, I want to attach or remove Tags by hand and have roster Tags refreshed on import, so that groups stay correct.
24. As a Staff member, I want to create a Manual Link or revoke a Link after checking identity myself, so that students without email are not stuck.
25. As a Staff member, I want to write an announcement in Thai (and optionally English), pick an Audience by attributes, Tags and Link status, see the live recipient count and the number of metered pushes it will cost, and send now or at a scheduled time, so that I send the right message to the right people at a known cost.
26. As a Staff member, I want to see per-announcement delivery and acknowledgement statistics (acknowledged / in Audience, sent / failed / skipped per Channel), so that I can follow up.
27. As a Staff member, I want to edit an announcement (updating it on channels that allow edits), re-send it explicitly, or retract it, so that mistakes are fixable.
28. As a Staff member, I want a usage page per Channel showing metered pushes this month against the cap, a 30-day chart and failures, and a banner when 80% or 100% is reached, so that I never hit the limit by surprise.
29. As a Staff member, I want to see Security Events (lockouts, duplicate link attempts, Staff lockouts), so that I can spot abuse.
30. As a Staff member, I want the back office to be usable on a phone, so that I can act from anywhere.

Administrators (ผู้ดูแลระบบ)
31. As an Administrator, I want to create Staff accounts, define Roles from the Permissions Modules declare, assign several Roles per Staff, and set temporary passwords, so that access matches duties.
32. As an Administrator, I want every Staff write, export, login and sensitive read in an immutable audit log with before/after values, so that I can answer "who changed what".
33. As an Administrator, I want to edit user-facing texts and bump the privacy notice version from the back office without a deploy, so that wording stays correct.
34. As an Administrator, I want to create the first Administrator, run migrations and back up/restore from a CLI, so that I can bootstrap and recover.
35. As an Administrator, I want an email when a Channel reaches 80% and 100% of its monthly quota, so that I can act before messages fail.

Deployment author / Core maintainer
36. As a Deployment author, I want to assemble a Deployment from a builder (config, runtime services, Channels, Verification Method, Modules) and get every misconfiguration at build time, so that bad setups never run.
37. As a Deployment author, I want to declare roster columns, Student attributes, Roles, quotas, texts, branding and OTP parameters in one TOML file, so that customer specifics never touch the Core.
38. As a Deployment author, I want to write a Module with Permissions, Menu entries, Actions, back-office pages, texts, Jobs and migrations through one registrar, so that customer features plug in cleanly.
39. As a Deployment author, I want the same code to run on Cloudflare Workers and on a native binary, so that hosting is a customer choice.
40. As a Core maintainer, I want one contract test suite that every Channel adapter must pass, so that a new Channel is proven the same way.
41. As a Core maintainer, I want a Fake Channel that drives the whole flow in tests and e2e, so that no test needs LINE or Telegram credentials.
42. As a Core maintainer, I want CI (fmt, clippy, tests, wasm32 check) and release-plz publishing to crates.io, so that releases are routine.
43. As a Core maintainer, I want a fictional example Deployment with seeded data, so that the repo is demonstrable and the customer's repo stays private.

## Implementation Decisions

### Architecture (ADR-0001, 0005, 0006, 0007)
- Core = platform-neutral Rust library `harpseal` plus crates `harpseal-channel-line`, `-channel-telegram`, `-channel-fake`, `-runtime-cloudflare` (workers-rs, wasm32, D1, R2, Cron), `-runtime-native` (tokio, rusqlite, S3-compatible storage, timer, SMTP), `-cli`. `deployments/example/{deployment,native,worker}` is a fictional university. Edition 2024, MSRV 1.91, no platform feature flags in Core or channel crates, every Core crate compiles to wasm32.
- Web: axum everywhere (workers-rs `http` feature on Workers), maud + HTMX server-rendered pages, one shared layout and CSS for back office and Mini App, HTMX from a pinned CDN, system Thai font, `[branding] name, primary_color, logo` from the Deployment TOML (optional `font_url`).
- Persistence: SQL written once in SQLite dialect behind a `Db { query, execute, batch }` port; `batch` is all-or-nothing and the only transaction primitive (D1 has none). `.sql` migrations per crate and per Module, tracked in a `migration` table.
- Keys and time (ADR-0007): UUIDv7 as 36-char text primary keys generated from Clock + Random; natural keys are unique columns only; timestamps are integer milliseconds UTC; display converts to the Deployment time zone. Never measure durations with Clock on Workers (frozen within a request).
- Public API surface (ticket "Cargo workspace"): re-exports from the crate root, `pub(crate)` or `#[doc(hidden)] __internal` elsewhere, `#![warn(missing_docs)]`, `#[non_exhaustive]` on public enums; Kernel schema is not public API; Modules may call each other directly.
- Design A seam (prototype `prototype/core-traits`, chosen in ticket #4): trait objects plus a runtime registry. `Services` is a cloneable struct of six `Arc<dyn _>` ports: Db, FileStore, EmailSender, HttpClient, Clock, Random. The runtime crate returns a `Services`; the Core never names a runtime type.

```rust
// Channel: 5 required methods + Capability accessors (from the prototype; edit/delete/mini_app default to None)
trait Channel: Send + Sync {
    fn kind(&self) -> ChannelKind;
    async fn parse_webhook(&self, req: WebhookRequest) -> Result<Vec<Inbound>>; // BadSignature before parsing
    async fn download(&self, file: &IncomingFile) -> Result<Vec<u8>>;
    async fn send(&self, to: &ChannelAccountId, delivery: &Delivery, msg: &Message, locale: &Locale) -> Result<SendReceipt>;
    async fn set_menu(&self, to: &ChannelAccountId, menu: Option<&Menu>) -> Result<()>; // None = locked Menu
    fn editor(&self) -> Option<&dyn EditMessage>; fn deleter(&self) -> Option<&dyn DeleteMessage>;
    fn mini_app(&self) -> Option<&dyn MiniApp>; fn attachments(&self) -> Option<&dyn SendAttachment>;
    fn capabilities(&self) -> Capabilities; // derived from the accessors
}
enum Inbound { Follow, Text, File, Action, Blocked, Unblocked /* each with ChannelAccountId, Option<ReplyToken> (none on Blocked), event_id: Option<String> (LINE webhookEventId, Telegram update_id; the Kernel handles each id once per Channel) and redelivery: bool (LINE isRedelivery, informational) — #35; each variant #[non_exhaustive], built with Inbound::text/action/file/follow/blocked/unblocked + with_event_id — #44 */ }
// Module: name() + register(&mut ModuleRegistrar) with permission, menu_entry, action, back_office(permission, path, MethodRouter), public(path, MethodRouter) (overlaps refused at build time), messages, job, migration, import_format, export_format
// Deployment::builder().config(..).runtime(services).channel(..)*.verification(..).module(..)*.build() -> Result<Deployment, BuildError>
```
- `build()` validates: missing config/runtime/verification/channel, duplicate channel kinds, duplicate Action ids, Role naming an unknown Permission, back-office route with unknown Permission, `Button::MiniApp` used on a Channel without a Mini App URL (new), unknown catalog keys referenced by Menu entries.
- Reply vs Push: `Delivery::select(reply_token, now)` is the only place the choice is made; the Kernel sends a handler's whole `Vec<Message>` as one batch per reply token (LINE tokens are single-use; > 5 objects → the rest go as Push and are metered). Adapters report `SendReceipt { message_id, metering: Metered | Free, metered_units, pushed, replayed_units }` (one metered unit per Push request to one recipient, #35; a unit answered 409 is metered only when no Outbound Message row of the same batch key and Message index records it (rows carry `msg_index` and `units`, #62)); the Kernel writes an Outbound Message row per send and upserts `usage_daily` (adding the units) in the same batch. A send the Channel stops part-way is recorded as far as it went and returned as `Error::PartialSend { sent, total, source, resume, key, .. }` (#35); a resume passes the whole batch to `Deployment::send_batch_with` with `SendOptions::resume_after(&err)` (#62, ADR-0010).
- Message model (ADR-0003, confirmed by prototype `prototype/message-render`): `Message::{Text, Card, CardList, Choices, Attachment}`, `Button::{Action, MiniApp}`, `Menu`, `ActionId` ≤ 64 bytes enforced by its only constructor. No image, date, Markdown, silent flag, URL button or Menu icon in the first slice. Outbound `Attachment` (with `size_bytes`, `url`) is a Capability, not part of the Channel minimum (receive text/files, send Text/Card/CardList/Choices, set Menu, report metering).
- Rendering and degrade rules are owned per adapter and documented with it (`docs/prototypes/message-render.md` tables are the spec): LINE = Flex bubble/carousel, quick reply, postback `data` = ActionId, rich menu per Menu with an image from the LINE channel config (#92: a LINE channel with credentials refuses to start without valid locked/unlocked images; the example bundles defaults drawn on the grid and accepts `LINE_MENU_IMAGE_LOCKED`/`_UNLOCKED` overrides natively), > 12 Cards → several carousels, quick reply > 13 or label > 20 → one bubble with all buttons, text > 5000 split; Telegram = HTML text (escaped) + inline keyboard, one message per Card (no carousel), text > 4096 split with the keyboard on the last part, `setMyCommands` scope chat + `setChatMenuButton`, commands mapped back to Actions through the account's current Menu, inline keyboard capped at 100 buttons with follow-up messages. No Action button may ever be dropped silently.
- Email: `EmailSender` first adapter = Resend HTTP API (both runtimes via `HttpClient`); runtime-native also offers SMTP.
- Jobs: single `job` table; a per-minute ticker (Cron trigger on Workers, timer on native) claims with one UPDATE (`state='queued' AND run_at<=now`, limit n, lock token, `locked_until`), stale locks are re-claimed, retry 3 with backoff 1/5/30 min, handlers idempotent, done rows pruned after 30 days.

### Kernel data model (ticket #7 plus deltas from #8, #9, #10)
Kernel tables: `student` (student_code unique, display_name, email, locale, status active/left, attributes JSON per the TOML schema, manual_overrides JSON, verification_locked_until, roster_imported_at), `tag`, `student_tag` (source roster/manual), `channel_account` (channel + external_id unique, first_seen_at, platform_locale, blocked_at, flow_state, flow_data JSON, consent_pending_version), `link` (status active/unreachable/revoked, method email_otp/manual, verified_by_staff_id, linked_at, revoked_at, revoked_by; at most one active per (student, channel) and per channel_account; history kept), `verification_challenge`, `consent` (per Student per notice version, never deleted), `security_event`, `inbound_message`, `staff`, `role`, `role_permission` (permission ids are code-declared, no table), `staff_role`, `staff_session` (id = token hash), `app_session`, `outbound_message` (pruned after 90 days, configurable), `usage_daily` (forever), `job`, `audit_log` (append-only, actor/action/target/before/after/ip/user_agent/request_id, secrets redacted, forever), `setting` (catalog text overrides and the Consent notice version only), `roster_import`, `migration`.
Module tables (announcements): `announcement`, `announcement_text` (per Locale), `announcement_delivery` (per Student per Link: pending/sent/failed/skipped, acked_at).
Precedence for texts: Module default (Thai + English shipped in Core, keys `kernel.<area>.<name>`, `announcements.<name>`) < `[texts]` in TOML < `setting` row.

### Chat flow (ticket #9), owned by the Kernel; Modules never see pre-Link Inbounds
State on `channel_account.flow_state`: `new → awaiting_consent → awaiting_student_id → awaiting_otp → linked`, plus `awaiting_reconsent`. Steps: welcome Text + Consent Card (accept / read full in Mini App `/notice`, no decline button; any other input re-sends the Card) → ask student id (pattern from TOML; not found and `left` share one text; no email → contact Staff; id already linked on this Channel → refuse, Push a warning to the old account, Security Event; locked → minutes left) → Verification Method `start` → Choices with masked email and buttons resend / cancel → `check` (digits only after stripping spaces/dashes, wrong = attempts left, 3 wrong = 30-minute lock on the Student + Security Event + Push to the Student's other Links, expired = resend, resend > 3/hour = wait) → on success, in one batch: active `link`, `consent` row (version remembered from the Card), Menu unlocked, success Card + Choices listing the Menu once; audit `link.create`.
Locked Menu: LINE rich menu with one "เริ่มใช้งาน" area; Telegram `/start` only. After Link, free text/file → one fallback Text + Menu Choices per hour, input stored as `inbound_message`, files downloaded at once (20 MB default). Unlink by Student (config default on): Menu entry → confirm Choices → revoke, locked Menu, goodbye Text, state back to `awaiting_student_id` (Consent kept). Unlink by Staff → Push notice + locked Menu. Manual Link → Push notice + Consent Card; Menu unlocks after accept. Blocked (LINE unfollow or a 403 on send) → `unreachable`, skipped by sends; any Inbound → `active`, welcome-back Text, Menu unlocked, no new OTP. Re-consent: next Inbound gets the new Consent Card, the Action is parked and replayed after accept; Pushes continue meanwhile. Menu label edit (#66, ADR-0011): a back-office save makes a new Menu revision and a background Job moves every linked Student of that Locale to it without waiting for an Inbound (accounts the platform can no longer reach are skipped and marked `unreachable`); the previous revision is removed only once the platform confirms nobody is left on it (LINE batch control, up to a few hours); the Menu shown before the first edit, which another Deployment on the same LINE account may share, stays until the next rich menu generation; a restored backup draws a new revision salt and drops the original's pending retires.
OTP defaults (TOML): 6 digits, 5 minutes, 3 wrong attempts, 3 resends per hour per student id, 30-minute lock.

### Roster import (ticket #8)
CSV (UTF-8, BOM tolerated, `,`/`;` auto-detected) or XLSX, every visible sheet (calamine, accepted +460 KB wasm; #70: the public `harpseal::sheet` reader finds the header in the first 10 non-empty rows, skips only labelled footer rows when the caller opts in, shows skipped rows and hidden sheets in the preview, refuses a `full` import when a hidden sheet holds the roster header, keeps whole numbers below 2^53 exact and reports longer ones as unreadable, and gives Modules an exact scaled parser for money). Mapping declared once in `[roster]` of the TOML (headers must match exactly; template download). Modes `full` (missing Students become `left`: all Links revoked, rows kept) or `upsert`. Preview first with counts (new / updated / unchanged / will-become-left / returning / skipped-by-manual-override), names that will become left, red warning when left > 20% or the file is smaller than the roster. Whole file rejected on any row error with a downloadable report; empty email allowed with a warning. Import runs as a Job in chunks of 500 rows (one `batch` each, idempotent), last chunk applies `left`; only one import at a time; file kept in FileStore for one year. Manual edits win: each hand-edited field is listed in `student.manual_overrides` and skipped by imports until "ใช้ค่าจากทะเบียน" clears it. `roster` Tags are replaced per Student on import; `manual` Tags are kept. No promotion feature: the new term's file carries the new year. Modes (#79): `[roster] modes` lists the allowed import modes (default both) and `default_mode` the preselected one (default `full`); a disallowed mode is refused with 400 at upload and at confirm (so an old `full` preview cannot be confirmed after a Deployment goes upsert-only), and a request without a mode uses `default_mode`, never `full` implicitly. #71: roster problems are blocking or warnings. Blocking: empty/malformed student id, duplicate id in the file, unreadable or off-type value, missing required value, hidden roster sheet in a full import. Warnings (the row imports and is listed in the preview and in report.csv): missing email, malformed email, an email used by another Student (in the file or already in the system), an empty optional attribute; `[roster] blocking` makes a warning class blocking. The Students list has a "missing data" filter and badge (no email, invalid email, attribute with no value); the chat claim refuses an invalid or shared email before sending a code (Security Event `link.shared_email`). #81: an integer or number attribute may declare an inclusive `min`/`max`; a value outside it is a blocking import problem and the Staff edit form refuses it. An enum attribute may declare `value_labels` per configured Locale; Staff see the label (falling back to the default-Locale label, then the value), stored values and filters stay the value, a roster cell may hold the value or its default-Locale label (exact after trim, ASCII case-insensitive), and the build refuses labels that make two values look the same in any Locale.

### Announcements Module, back office, Mini App (ticket #10, look & feel from ticket #5)
Announcement fields: title + body per Locale (Thai required), Audience JSON (AND of attribute filters where multi-value = OR, Tags, Link status; live count; not saved separately), send now or scheduled, expires_at, require_ack. Sending: parent Job snapshots the Audience into delivery rows (one per active Link) and spawns child Jobs per Channel (LINE multicast 500 per call, Telegram chunks of 25 paced to the limits); `unreachable` → skipped, never re-sent; the send page shows the pushes it will cost. Acknowledge: Action `announcements.ack.<id>` or the Mini App button sets `acked_at` on all of that Student's delivery rows (idempotent, second tap answers "รับทราบแล้ว"); stats = Students acked / Students in Audience plus per-Channel counts. Edit updates text and calls EditMessage where available; "ส่งซ้ำ" is a separate counted send; retract hides from Mini App and Menu, deletes where DeleteMessage exists, no notice; a tap on a retracted Card answers "ข่าวนี้ถูกถอนแล้ว". Menu entry "ข่าวล่าสุด" = Card List of the 5 newest unexpired, unacknowledged first, plus "ดูทั้งหมด" (Mini App). Hand-picked list (#76): an Audience may name Students by student ID (at most 2,000, counting ids that fit no pattern), ANDed with the other filters and alone the whole Audience; unknown ids and Students without a live Link are reported in the preview and never sent to; the preview reveals roster membership and Link status to anyone who may send (owner decision); the list is saved with the announcement and audit rows record its size, not the ids. Follow-ups (#77): Editing a sent announcement offers "notify recipients of the edit" (off by default), beside the number of LINE recipients and this month's Quota use, with a warning when the notice would go over it (it still sends). It needs a changed text and an announcement that has not expired. On a Channel that cannot edit a sent message (LINE) each recipient whose text changed (the newest delivery per live Link, including those who already acknowledged; their acknowledgement stands) gets one short Push linking to the updated announcement, metered and keyed per edit version and recipient; every edit with the notice notifies again. Telegram keeps editing in place. A later notice supersedes a running one; a retracted or expired announcement sends none, and an expired one cannot be resent. The Menu's "ข่าวล่าสุด" lists `[announcements] latest` items (default 5, 1–10), "ดูทั้งหมด" stays. Past its expiry an announcement is closed to Students: opening it from a Card or the Mini App, or acknowledging it, answers "no longer available" and records nothing; Staff still see it, marked expired.
Back office (9 pages): Login; Students (card list on phones with name, code, programme/year, Link icons per Channel; table at ≥ 900 px; detail with Links, Manual Link/revoke, edit, Tags); Roster import; Announcements (list, create, detail + stats, resend, retract); Usage; Security Events; Audit; Staff & Roles; Texts. Permissions: `kernel.student.view/edit`, `kernel.link.manage` (Manual Link), `kernel.link.revoke` (Staff unlink, #80), `kernel.roster.view/edit/import`, `announcements.view/send/retract`, `kernel.usage.view`, `kernel.security.view`, `kernel.audit.view`, `kernel.staff.manage`, `kernel.setting.edit`. Example Roles: Administrator (all), Officer, Viewer.
Staff auth: email + password ≥ 12 chars, Argon2id m=19456 t=2 p=1 as a PHC string (measured ~55 ms CPU on Workers), cookie HttpOnly + Secure + SameSite=Lax, 12-hour sliding session, 7-day absolute, 5 failures → 15-minute lock + Security Event, first Administrator via `harpseal staff create --admin`, password reset = Administrator sets a temporary password that must be changed at next login.
Usage: per Channel metered pushes this calendar month vs the TOML cap, 30-day chart, failures, all from `usage_daily`; 80% → banner on every page + one email to Administrators per month; 100% → red banner + second email; sending is never blocked automatically.
Mini App: one page (Link status + my announcements with expandable bodies and one-way acknowledge, unacknowledged first) plus public `/notice`; not linked → page says to go back to chat; App Session = exchange LIFF id token / Telegram `initData` for a 1-hour cookie bound to the Channel Account. Module pages (#72): a Module outside the Core serves Mini App pages under `/app/` whose handler takes `AppStudent` (the App Session's linked Student; without a session, the Kernel's entry page) or `AppForm` for plain forms; any method other than GET/HEAD/OPTIONS is refused when cross-site and needs the session's CSRF token; every `/app` response is `no-store`; Students see only roster attributes marked `student_visible`; Modules list pages on the Mini App home with `ModuleRegistrar::mini_app_link(label_key, path, order)`, and `build()` refuses a link that is not the Module's own plain `/app/` route. App Session (#86): An App Session lasts one launch at most, ends after `[mini_app] idle_minutes` (default 15) without use and one hour after the exchange, and belongs to the browser tab that signed in. A Mini App page load that does not come from one of the Deployment's own pages (opened from the chat, a Card's deep link, a bookmark) drops the session before any Student data renders and asks the platform again who is there (LIFF ID token, Telegram `initData`); a different user gets their own session or the "not linked" page. Navigation inside the Mini App continues the launch. The Student can sign out from the home, which ends the App Session at once. Verify calls are counted per IP group before calling the platform (`[mini_app] verify_per_minute`, default 300) with a separate budget for refused tokens, and an account keeps at most 5 live sessions.
Module API for Deployments' own Modules (#69): a Module outside the Core uploads spreadsheets through `ModuleRegistrar::sheet_upload` and the `Uploads` extractor (Permission, CSRF, 4 MiB, CSV/XLSX sniffed; kept uploads bound to the Module and uploader, pinned for a week on confirm, never cancellable after confirm, excluded from backups, swept after 24 h; #74), and notifies chosen Students with `JobContext::notify` / `PageState::notify` (chat Push when linked, metered like Kernel sends; email otherwise with an idempotency key; Module-scoped keys, atomic claims, quota exhaustion falls back to email or defers; at most a request budget per call; #73). Webhooks (#97, ADR-0009): after the signature check and the claim the webhook answers 200 and the handling runs in the background (native task, Workers `ctx.wait_until`), one account at a time in order; a claim is renewed when handling starts and an event swept as lost while queued is skipped. LINE rich menus (#98): a reused rich menu found without its image is repaired (image uploaded, link retried once) in `set_menu` and in the bulk re-link; a rich menu is never deleted to repair it. Settings (#75): a Module declares a typed Setting for the whole Deployment with `ModuleRegistrar::setting(key, kind, default, permission, label_key, help_key)`; kinds are text, multi-line text, whole number, date, https URL or account number (digits, `-`, single spaces, a digit at both ends). The server checks the kind on every save and refuses invisible and text-direction characters for every kind. `/admin/settings` lists the Settings; only Staff holding a Setting's own Permission can change it, `kernel.setting.edit` alone shows it read-only. A stale form is refused (compare-and-set token) and every save writes an audit row with the value before and after. A saved value that fails its check reads as `SettingNotSet`, never the default; only the Kernel declares `kernel.` keys and a setting key may not also be a text key. Values live in the Kernel's `setting` table with no Locale (no Locale in `deployment.toml` may be empty), so Backup and restore carry them. #103: a Module may declare a Setting with no default (`setting_without_default`); reading it returns `SettingNotSet` until Staff holding its Permission save a value, `/admin/settings` shows it as not set yet, and a backup carries it as is. Module code saves a Setting with `Settings::save` only as Staff holding the Setting's Permission; a Deployment's seed or CLI, holding the `Deployment`, saves as the system with `save_setting_as_system`; both apply the kind check and write the same `setting.update` audit row. The `kernel.` namespace belongs to the Kernel: a Module named `kernel` or `kernel.…`, or declaring a Permission, Action or text key starting with `kernel.`, fails the build. #106: a Module's back-office page or Job can call the Core's code-level services through `PageState::deployment()` / `JobContext::deployment()`; the reference is borrowed only, never kept beyond the request or run. The Deployment's own methods (`save_setting_as_system`, sends, `run_job`, `tick`, `migrate`) check no Permission and are for the Deployment's own code, not for Staff actions. For a Staff action the signed-in Staff member acts as `Actor::staff` with the request's `RequestCtx` (e.g. `announcements::create_draft` / `confirm`); the Core checks that Staff member's Permission and audits the write as on its own pages. `ui::service_error` answers a refusal with the same 403 page, a conflict with a 409 reload page, anything else with a 500 page that never shows the error text. #110: Roles from `[roles]` are seeded once: a `migrate` creates a Role name and grants a (Role, Permission) pair only the first time it sees it (recorded in `role_seed`, backed up with the rest; a forced restore of a backup without it empties it), so an Administrator's edits on Staff & Roles (a Permission removed, a Role deleted) survive every deploy, and a Permission added to `[roles]` later still arrives once. Announcement body format (#108): the body (at most 2,000 characters) is a small Markdown subset stored as text: line breaks, `**bold**`, `*italic*`, `- ` and `1. ` lists (1-99), `[text](https://…)` links and bare `https://` URLs. Only vetted `https:` links are kept; anything else, and all HTML, stays text; the parser is linear. The Mini App renders it and links open outside the chat app; the back-office editor has a toolbar and a live preview. In chat the Card body is plain text and the Card carries a `Button::Url` (https only, checked again by each adapter) for each of the body's first two distinct links after "เปิดดูรายละเอียด"; the "ข่าวล่าสุด" list shows plain text (ADR-0003 amended). #115: Staff holding `kernel.setting.edit` pick the Deployment's LINE Official Account package (Free 300, Basic 15,000, Pro 35,000 messages a month, figures from LINE for Business Thailand read on 2026-11-08, or a Custom number) on `/admin/usage`; the LINE Quota follows it at once, `[quotas.line] metered_per_month` being the default and the Custom value until a first save (and again after "use the configured value"). The choice is a `setting` row (`kernel.usage.line_package`), audited and carried by Backup; every reader of the cap reads the effective limit when it runs, and the Quota email record keeps the limit it measured against, so a switch starts the emails over. Quota exhaustion is unchanged. Branding (#114): `/admin/branding` (`kernel.setting.edit`) sets the institution's display name, primary colour (`#RRGGBB`, white text at least 4.5:1) and logo (PNG/JPEG, ≤ 256 KB, 16–1024 px), with a preview of the back-office and Mini App headers before saving; they are Kernel settings, `deployment.toml` values apply until a save and a reset returns to them. The same page replaces the LINE rich menu images (checked against LINE's rules and the Menu grid, tap areas previewed); a save creates the new rich menus on LINE first and saves nothing if LINE refuses, then re-links every account and retires the old menus (ADR-0011); a reset returns to the bundled or environment images the same way. Every change is audited and carried by backups. Announcement images (#109): an Announcement may carry up to 4 JPEG or PNG images (checked by their bytes, at most 1 MB, 4096 pixels a side and 16 megapixels each, never resized); `![alt](image:N)` places image N and the Mini App shows images in place with alt text. The pushed Card shows the first placed image (else image 1): the Flex hero on LINE (20:13, cover, no extra message), the link preview on Telegram. Images are served on unguessable public URLs (128-bit tokens) under the Deployment's `public_url`, only while the Announcement is sent and not expired; without `public_url` chat Cards carry no image. Before sending, removed files are deleted; after sending they stay on their URLs for delivered Cards until retract or expiry. Backup and restore carry them; purge is not in this slice. Announcement headings, colours and PDFs (#113): the body format adds `## ` and `### ` heading lines and coloured text `{red}…{/red}` from a fixed palette (red, orange, green, blue, grey; each at least 4.5:1 on the Mini App's surfaces; no free colours); the Mini App shows both, chat shows a heading as a plain line and drops colours. An Announcement may carry up to 3 PDF files (checked by their bytes, at most 10 MB each, one new file per save; files with script, embedded files, launch, form submission, remote go-to, XFA or rich media, or left unclosed, are refused where a quick best-effort scan finds them), stored, served and backed up like images on unguessable public URLs only while the Announcement is sent and live, with their file names kept; the Mini App lists them and the pushed Card gives the first one a URL button within the two-URL-button budget (only with `public_url`), which LINE opens in the phone's browser.

### Runtimes, example Deployment, delivery process (tickets #6, #5, #11)
- Workers Paid is required (Free's 10 ms CPU fails logins and imports); release profile `opt-level="z"`, `lto`, `codegen-units=1`, `panic="abort"` + panic hook; worker-build with `wasm-opt -Oz`; measured 0.8 MB wasm, 4–7 ms startup.
- `deployments/example`: fictional "Seal Bay University", Thai default Locale, 50 Students, 3 Roles, sample announcements, LINE + Telegram + Fake channels.
- Implementation starts from branch `prototype/workers-pages` (phase 1 removes the bench/seed toys and applies the API rules), lands on main by PR. Nine phases, at most two workers in parallel on disjoint crates: 1 Kernel base → 2 Channels ∥ runtimes → 3 identity flow ∥ 4 Staff auth + shell → 5 roster import ∥ 6 Jobs + announcements → 7 usage/security/audit pages ∥ 8 Mini App → 9 example data + e2e + CI + release-plz + CLI.
- Backups (#88, ADR-0008): a backup writes each table in ordered parts (format 2; `tables/<t>.ndjson`, then `tables/<t>/00001.ndjson`, …), each pinned by its SHA-256 and row count. A part ends at `[backup] part_rows` (default 20,000) rows, once it passes `part_mb` (default 8, max 32), or where a nightly Job step ran out of budget, and the next step reads on after the last key. A Worker backs up a table of any size holding one part in memory at a time (plus ~16 B per row per UNIQUE index); `max_table_rows`/`max_table_mb` are removed. A table read over several steps has its UNIQUE keys checked across its parts and stale rows read again, so a backup marked done restores (Kernel tables). Restore checks every part's name, order, hash and row count, then keys and foreign keys, before any write, and needs about 7x the NDJSON size in memory (native only). Format-1 backups still restore.
- Owner checklist (blocking phase): reserve `harpseal*` crate names [1]; `CARGO_REGISTRY_TOKEN` secret [9]; Workers Paid [2]; LINE OA + Messaging API + LIFF + rich menu images [3]; Telegram bot + Web App URL [3]; Resend account + domain [3]; delete `harpseal-proto-*` [now]; remove the customer name from CLAUDE.md and add LICENSE [before public]; install `just` [9].

## Testing Decisions

- A good test drives the system through the seam a caller uses and asserts on what a Student or Staff member would observe (messages sent, pages rendered, rows a later request reads back), never on internal structs or SQL.
- **One seam:** a `Deployment` built with the Fake Channel and fake Services (in-memory SQLite `Db`, an `EmailSender` that captures the OTP, a controllable `Clock`, a recording `HttpClient`), exercised through its axum Router: Fake Channel webhook calls for the chat flow, HTTP requests for back-office and Mini App pages. Every flow in this spec has a test at this seam; the Fake Channel exposes what the Student saw (messages, Menu state, metering).
- **Contract tests:** one suite generic over `dyn Channel`, run against the Fake Channel and against the LINE and Telegram adapters with the recording `HttpClient` (signatures, parse of recorded webhooks, send/menu payloads, metering, degrade rules, Capability accessors agreeing with `capabilities()`).
- **Unit tests** only for pure functions: renderers (snapshot JSON as in `prototype/message-render`), roster validators and mapping, Audience filter resolution, degrade helpers, password hashing, Delivery selection.
- Runtime crates: `cargo check --target wasm32-unknown-unknown` in CI; behaviour on Workers proven by the owner's manual check on a preview and the measurements already recorded.
- `just e2e` (outside CI) boots `deployments/example/native` with the Fake Channel, imports the example roster (CSV and XLSX), walks Consent → OTP → Link → Menu → announcement → acknowledge → unlink and prints pass/fail; the coordinator runs it before merging flow/announcement/import tickets, the owner before every release. The Mini App ticket also requires a manual check inside real LIFF and Telegram webviews.
- Prior art: the three prototype branches (`prototype/core-traits`, `prototype/message-render`, `prototype/workers-pages`) hold the snapshot-JSON tests and the Fake Channel shape to build from.
- CI per PR: rustfmt, clippy `-D warnings`, `cargo test --workspace`, wasm32 check; definition of done adds new-behaviour tests, contract suite green, docs/GLOSSARY/ADR updated, no customer name, `missing_docs` clean.
