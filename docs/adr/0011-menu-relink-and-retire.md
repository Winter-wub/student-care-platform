# A Menu label save re-links in bulk and retires this Deployment's salted revisions after a confirmed batch

Until #66 a back-office edit of a Menu label reached a Student only at their next `set_menu`, and on LINE each edit left one more rich menu under the same generation, kept on purpose because the adapter could not tell an older version of this Deployment from another Deployment's live one (#63's KEEP rule).

Now each save of a Menu label records the next **Menu revision** of every effective Locale whose labels change (`menu_revision`, migration 0011; revision 0 is the Menu shown until then, with its labels) and enqueues one Kernel Job per such Locale in the same batch as the `setting` write. The first save also draws the Deployment's **revision salt** (`menu_salt`: 4 random bytes from the Random port, stored once, backed up with the database and drawn again by a restore). Every Menu the Kernel sets carries the newest revision and the salt. The Job re-links every linked account of that Locale (`Channel::relink_menu`, chunked and resumable; an unreachable account is passed over and its Link marked unreachable, so one dead account never holds the others back) and only then retires the older revisions (`Channel::retire_menus`), handing the adapter the older revisions as whole Menus. A retire still pending on the platform is stored per Locale and Channel (`menu_retire`); a newer run takes it over and starts nothing new until it is finished. When everything is retired, accounts locked since the run started get the locked Menu again.

On LINE a revisioned rich menu is named `harpseal-<key>-<gen>-r<rev>-<salt>-<hash>`. The adapter re-links with `bulk/link` (500 ids a call, 2,000 requests a second) and retires through batch control (`POST /v2/bot/richmenu/batch`, link from each previous rich menu to the new one, then the progress endpoint until `succeeded`, polled after 5, 10, 20 and 40 minutes then hourly, then the deletes). It moves and deletes only names that carry this Deployment's salt.

We rejected bulk link alone: it answers 202 and works in the background, and the only way to confirm it is one `GET` per user, so a delete after it could strand accounts on the default rich menu. We rejected batch control alone: it allows 3 requests an hour, so a few edits in a row would delay the new labels by up to an hour; with both, the labels change within one Job run and only the cleanup waits. We rejected naming a revision without a salt: two Deployments on one token (production and staging) both reach revision 3, and both show revision 0 with the default labels under the same name, so a retire by name would move the other's Students onto our labels and delete their rich menu. Revision 0 therefore is never retired: it stays until a generation bump, as before #66. We rejected sending a new batch while an earlier one is ongoing: LINE applies each batch to the users linked before its request, so a leftover batch could move users onto a revision the newer batch then deletes.

## Consequences

- Public API additions: `Menu::with_revision` / `revision`, `Menu::with_salt` / `salt`, `Channel::relink_chunk` (default 20), `Channel::relink_menu` (default: `set_menu` per account, an `Error::Unreachable` account skipped), `Channel::retire_menus` (default: retire nothing), `MenuRelinked { done, error, skipped }`, `MenuRetire`. LINE: `richmenu::{BULK_LINK_MAX, RELINK_CHUNK, SALT_LEN, PROGRESS_FIRST_POLL_SECS, PROGRESS_MAX_POLL_SECS, BATCH_RETRY_SECS, poll_delay}`; `richmenu::name_key` also reads salted names. Telegram: `TelegramConfig::menu_relink_chunk` (default 20: 40 calls, under the Workers free plan's 50 subrequests).
- Every Menu the Kernel sets carries the newest revision and the salt: one more query per unlocking `set_menu`; a failure of that query fails the turn, like any other database failure there.
- A run waits at most 200 times (rate limits, polls); past that its Job fails with an error the Jobs status page shows, and the revision stays `linking` until the next label save in that Locale picks it up. Chunks of accounts do not count as waits.
- Telegram re-sets the per-chat commands of every linked account (two calls each) and has nothing to retire.
- A save that changes the default Locale's label also re-links the Locales that fall back to it for that key.
- A restore draws a new salt (`backup.restore` audit row: `menu_salt_redrawn`), so a copy of production restored into staging on the same token never shares its names. Rich menus named with the old salt are never retired by the restored Deployment: they leak until a generation bump, the safe direction. The restore also clears pending retires (`menu_retire`) and marks queued re-link Jobs failed, so the copy never polls the original's batch nor links its users.

## Amendment (#114): Menu images saved in the back office

`/admin/branding` replaces the image a Menu is drawn on. The image is part of a LINE rich menu (its `<hash>`), not of the Menu's entries, so a new unlocked image is recorded like a label save: the next Menu revision of every Locale, with the same entries, and one re-link Job each. The new rich menus are created on LINE first (`MenuArt::stage`); if LINE refuses a create or an upload, nothing is saved or audited and no account moves. Only then does one batch save the settings, the revisions and the Jobs.

The retire now matches a previous revision by Menu key, generation, `r<revision>` and salt, whatever its hash, instead of recomputing the exact name each revision had: that name depended on the image in use when it was made, which may since have changed. The salt still makes the name this Deployment's, and only revisions handed over are moved and deleted, so the KEEP rule holds.

The locked Menu has no revisions of its own. Once its image changes, it gets one (the setting `kernel.branding.menu_locked_revision`, bumped on each change, a reset included), named `harpseal-locked-<generation>-r<revision>-<salt>-<hash>`. A Job (`kernel.branding.relock`) shows it to every account that is not linked (read again just before each set, so one that links meanwhile keeps its unlocked Menu; one failing 5 runs is passed over), a page of 20 per run, then retires the older salted locked revisions through the same batch control (`menu_retire` row with Locale `~locked`). The unsalted locked rich menu that came before the first change is revision 0: it is never retired, as before. A restore cancels this Job too.

A rich menu can exist at the newest revision without being the one shown: a stage whose save then lost (another save came first), or a `set_menu` racing a save that drew the old image under the new revision. Nothing links to such an orphan for long (the re-link moves everyone to the one built from the saved image), and it is never retired at its own revision, but it is retired with that revision when the next one comes, since the retire takes any hash at a revision handed over. A stage that would take the channel past LINE's 1000 rich menus is refused before it creates any. The revision salt is stored before the stage (when there is none yet) and read back, so the staged names and every later retire use the same salt even when two first saves race.

Consequences: `Channel::menu_art` (default `None`) and `MenuArt`, `MenuImages`, `MenuSlot`, `MenuLayout`, `MenuArea`, `MenuImageProblem` are public API; every Kernel Menu set reads the saved images first, one more query per `set_menu`.
