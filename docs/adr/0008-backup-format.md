# Backup format: a directory of NDJSON tables, a manifest, and FileStore objects, through the ports

`harpseal backup` writes a directory (format 1): `manifest.json` (Deployment name, `taken_at`/`finished_at`, the applied migrations in applied order with their checksums, each table's columns, row count, `CREATE` SQL and the SHA-256 of its entry, each FileStore object's key, size and SHA-256), one `tables/<table>.ndjson` per table (one JSON object per row, every column; integers as `42`, reals as `3.0` (exact round trip), text as strings, `null`, blobs as `{"$blob": "<base64>"}`), and `files/<sha256 of key>` for every object a `file_key` column names. The manifest pins every entry, so its own SHA-256 (recorded in the restore's audit row) identifies the whole backup. It is read and written only through the `Db` and `FileStore` ports and the async `BackupSink`/`BackupSource` traits, so the same code and format serve rusqlite and D1 (and could be stored in R2 or S3). The `migration` table is not dumped: a restore checks, per Module, that the backup's migrations are the first of that Module's in the Deployment, applies only those, inserts the rows, then applies the newer migrations so data migrations run over the restored rows.

We rejected copying the SQLite file (native only, no D1, and it ties a backup to the exact schema and file layout), `wrangler d1 export`-style SQL dumps as the format (dialect- and schema-coupled, and they replay `CREATE` statements the migrations already own), one JSON document per table (does not stream, and one bad row spoils the table), and checking the migration list as one global prefix (the applied order interleaves Modules when a Kernel migration ships after a Module's, so a Deployment's own backup would be refused).

`restore --force` deletes the rows of every table in the backup, `audit_log`, `security_event` and `consent` included, in one batch that drops their append-only triggers and re-creates them from the saved SQL. This is the one exception to ADR-0007's "no code path deletes the audit log": the backup's own audit rows replace them, and the `backup.restore` audit row, written in the same batch as the last restored rows, records the manifest's SHA-256, the rows deleted per table and the id and time of the newest audit row deleted.

## Consequences

- Backups taken by one build restore into the same or a later build of the same Deployment; a migration that drops a column or adds a `NOT NULL` column without a default still applies after the rows go in, but a database already ahead of the backup is checked column by column and may refuse.
- The dump is not one transaction (the `Db` port has none for reads): stop the Deployment for a point-in-time backup and for every restore. Online backups are allowed since #78 (see the amendment below).
- The backup carries secrets (password hashes, session ids) and personal data: it is as sensitive as the database. `--drop-sessions` ends restored sessions.
- A backed-up table with an `INSERT` trigger is refused on restore (the trigger would fire per row); a Module that needs one must change this rule first.
- A format change bumps `format`; `restore` refuses formats it does not know.

## Amendment (#78, 2026-11-07): online, chunked backups

The nightly backup Job dumps format 1, unchanged, while the Deployment runs, over several Job runs (a saved resume point next to the backup). The format is the same; what changed is how a dump reads and what a restore checks:

- **Keyset paging.** A table is read in primary-key order, each page after the last key read (`rowid` only for a table without a primary key, which the Kernel does not have). A row deleted and re-inserted under the same key mid-dump is read at most once, so no entry holds a duplicate key. An entry's rows are therefore in primary-key order, no longer `rowid` order; a restore never relied on the order.
- **Children-first order.** Tables are dumped children before parents, so a row added mid-dump never references a parent missing from the backup. The Kernel deletes no referenced row except a Role, whose grants cascade.
- **Pre-write validation.** Before it writes anything, a restore checks that no two rows share a primary key or a key of any `UNIQUE` index (partial and expression indexes evaluated by SQLite over the rows; one it cannot read refuses) and that every foreign key resolves among the backup's rows. Rows orphaned through an `ON DELETE CASCADE` key are dropped (the delete would have removed them) and counted in the audit row; any other problem refuses the restore with a report.
- **Per-table size limit.** A table is one entry built in memory. The Job counts rows and estimates the NDJSON size before reading a table and fails the run, naming it, above `[backup] max_table_rows` (default 150,000, so a table's queries fit one step) or `max_table_mb` (default 24, for a 128 MB Worker). On Workers there is no fallback inside the Deployment: until #88 (table parts, a table split over several entries; a format change, `format: 2`) the database is exported with `wrangler d1 export` meanwhile, which does not copy the files. A native server raises the limits or runs `harpseal backup`.
- **Subrequest budget.** A step stops before its own queries and FileStore calls would pass 350, so a Worker invocation (1,000 subrequests, shared by up to 25 Jobs per tick) keeps room for the others.
- **Left out.** Live Verification challenges are never dumped, and a restore never writes `backup_run` (the target's own list of backups).

## Amendment (#88, 2026-11-08): table parts, `format: 2`

A table is written in ordered **parts** instead of one entry, so a backup of any size fits a Worker. This replaces the per-table size limit of the #78 amendment: `[backup] max_table_rows` and `max_table_mb` are gone (an old `deployment.toml` that sets them is refused at boot, naming the key), and with them the `wrangler d1 export` fallback.

- **Layout.** Part 0 of a table is `tables/<table>.ndjson` (the format-1 name), part `n` ≥ 1 is `tables/<table>/<n, five digits>.ndjson`, so a table of one part is laid out as in format 1. A table always has at least one part (an empty table, one empty part). A table name with `/` is refused by the dump.
- **Manifest.** Each table keeps `rows`, `columns` and `sql`, drops `sha256`, and lists `parts` in order, each `{entry, rows, sha256}`. `format` is `2`: a build that reads only format 1 refuses it by number instead of restoring part 0 alone. A table without `parts` (format 1, or one written by a run that started before the upgrade) is the one entry `tables/<table>.ndjson`, pinned by `sha256`; format 1 with `parts` is refused.
- **Part size.** A part ends at `[backup] part_rows` rows (default 20,000; its pages are cut to fit exactly), once its NDJSON passes `part_mb` (default 8, by at most one page of 500 rows), or where a Job step's budget ran out. One part is held in memory at a time, so a step's memory is bounded by the part size, not the table's. `harpseal backup` splits tables by the same settings (one code path), without the step budget.
- **Resume.** Between steps, the progress saves a cursor for the table being written: its parts so far and the key of the last row in them (keyset by primary key as before, never `OFFSET`). The next step reads on after that key. Before writing a part that the saved progress does not name yet, a step saves the progress (one more FileStore call, counted in its budget), so a run that dies leaves no entry that its progress does not name: a retry rewrites the same part, and retention deletes every part of a failed run.
- **Files per part.** Each part lists the FileStore keys its own rows name (`files`, sorted, each once), read from the rows as they are written instead of a `SELECT DISTINCT` over the table afterwards; the objects are copied once every table is written, in table and part order, each once. The progress keeps no separate key list.
- **Keys across steps** (#88 review). A table read over several steps, minutes apart without a snapshot, can hold a row changed after it was read next to a row read later that now has its key (a Link revoked and the Student linked again: two live Links). So when a table's rows are all written, its keys on every `UNIQUE` index but the primary key are checked across all its parts: SQLite computes each row's key terms and partial `WHERE` beside the row as it is read, and the dump keeps an 8-byte hash per row per index, in memory for the parts of the current step and as `<prefix>.check/<table>/<n>.keys` (headed by the part's SHA-256) for the next step. A part whose hashes are missing or stale, or that holds a repeated key, is read again over its key range and rewritten in place, after the progress saves it as to be read again (a crash mid-way reads it again). The database holds no two rows with one key, so this converges; after three rounds that still find repeats the step fails naming the table and index, and the run fails on its last retry. A backup marked done therefore restores. The hashes are deleted once the table is done; retention deletes those of an abandoned run.
- **Rolling back.** A build from before #88 reads neither a format-2 manifest nor its progress (both drop the table's `sha256`). Rolled back while a nightly run is under way, that run fails (retried, then emailed) and leaves parts 1 to n, its `.progress.json` and its `.check/` hashes in the FileStore, named by nothing the old build can read: delete `backups/<UTC time>/`, `backups/<UTC time>.progress.json` and `backups/<UTC time>.check/` by hand. Its retention also refuses every format-2 backup ("format 2 is not supported", a prune error on the Backups page) until they are deleted by hand or the build moves forward again; format-2 backups restore only with this build or a later one.
- **Restore.** Before anything is written, every part is read in order and checked: its entry must be the name of its index (parts listed in another order are refused), its bytes must match its SHA-256 and its row count, and the parts must add up to the table's `rows`; a missing part refuses. The rows of all parts then go through the same key and foreign-key checks as before, and are inserted as before. A restore holds the decoded rows of the whole backup in memory, as it did (about 7 times the NDJSON size, measured): it runs as `harpseal restore` on a native machine, not inside a Worker.
